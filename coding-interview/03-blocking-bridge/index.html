    3. Calling Blocking Code from WebFlux¶

    L2 ★★☆ · Mono.fromCallable, subscribeOn, dedicated bounded scheduler, Mono.just trap

    Problem¶

    A legacy CRM SDK is blocking (50 ms per call). Call it from a WebFlux service without blocking the event loop, make it lazy, give it a timeout, and stop a slow CRM from exhausting the threads that other blocking work needs.

    Key idea¶

    Wrap the call in Mono.fromCallable, which is lazy and runs once per subscription, and move execution with subscribeOn to a dedicated, bounded scheduler (Schedulers.newBoundedElastic(10, 100, "legacy-crm")). The tests prove which thread did the work, that nothing runs before subscription, and that Mono.just(blockingCall()) runs at assembly time on the caller's thread.

    flowchart LR EL["event loop (reactor-http-nio)"] -->|"subscribe"| FC["Mono.fromCallable(legacy::load)"] FC -->|"subscribeOn"| BP["legacy-crm pool (max 10 threads, queue 100)"] BP -->|"result"| EL2["continue the chain"] X["Mono.just(legacy.load())"] -.->|"runs NOW, on the caller"| EL

    Solution¶

    P03BlockingBridge.java
    package com.example.reactive.playbook.codinginterview;

import java.time.Duration;
import java.util.function.Function;
import reactor.core.publisher.Mono;
import reactor.core.scheduler.Scheduler;
import reactor.core.scheduler.Schedulers;

/** Problem 3: call a BLOCKING legacy client (JDBC, SOAP SDK) from WebFlux without blocking the event loop. */
public class P03BlockingBridge {

    /** The legacy API: blocks the calling thread. */
    public interface LegacyCustomerClient { String loadCustomer(String id); }

    private final LegacyCustomerClient legacy;
    private final Scheduler blockingPool;

    public P03BlockingBridge(LegacyCustomerClient legacy, Scheduler blockingPool) { this.legacy = legacy; this.blockingPool = blockingPool; }

    /**
     * fromCallable = lazy (runs per subscription), subscribeOn = WHERE it runs (a bounded pool for blocking work),
     * timeout = never wait forever on legacy I/O.
     */
    public Mono<String> customer(String id) {
        return Mono.fromCallable(() -> legacy.loadCustomer(id))
                .subscribeOn(blockingPool)
                .timeout(Duration.ofSeconds(2));
    }

    /** WRONG (for contrast): Mono.just evaluates eagerly on the CALLER's thread, i.e. the event loop. */
    public Mono<String> customerWrong(String id) { return Mono.just(legacy.loadCustomer(id)); }

    /** A dedicated, bounded pool: a slow legacy system can't exhaust the shared boundedElastic for everyone. */
    public static Scheduler dedicatedPool() { return Schedulers.newBoundedElastic(10, 100, "legacy-crm"); }

    public static Function<String, String> threadName() { return s -> s + " on " + Thread.currentThread().getName().replaceAll("-\\d+$", "-N"); }
}
    P03BlockingBridgeTest.java
    package com.example.reactive.playbook.codinginterview;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicReference;
import org.junit.jupiter.api.Test;
import reactor.core.publisher.Mono;
import reactor.core.scheduler.Schedulers;
import reactor.test.StepVerifier;

class P03BlockingBridgeTest {

    final AtomicReference<String> ranOn = new AtomicReference<>();
    final AtomicInteger calls = new AtomicInteger();
    final P03BlockingBridge.LegacyCustomerClient legacy = id -> {
        calls.incrementAndGet();
        ranOn.set(Thread.currentThread().getName());
        try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return "customer " + id;
    };

    @Test
    void blockingCall_runsOnTheDedicatedPool_notTheCaller() {
        var pool = P03BlockingBridge.dedicatedPool();
        try {
            StepVerifier.create(new P03BlockingBridge(legacy, pool).customer("c1")).expectNext("customer c1").verifyComplete();
            assertThat(ranOn.get()).startsWith("legacy-crm-");
        } finally { pool.dispose(); }
    }

    @Test
    void fromCallable_isLazy_nothingRunsUntilSubscribe() {
        Mono<String> mono = new P03BlockingBridge(legacy, Schedulers.boundedElastic()).customer("c2");
        assertThat(calls.get()).isZero();
        mono.block();
        mono.block();
        assertThat(calls.get()).isEqualTo(2);                  // runs once PER subscription
    }

    @Test
    void monoJust_blocksTheCallerAtAssemblyTime() {
        new P03BlockingBridge(legacy, Schedulers.boundedElastic()).customerWrong("c3");   // never subscribed!
        assertThat(calls.get()).isEqualTo(1);
        assertThat(ranOn.get()).isEqualTo(Thread.currentThread().getName());              // ran on the caller's thread
    }

    @Test
    void manyConcurrentCalls_doNotSerialise() {
        var pool = P03BlockingBridge.dedicatedPool();
        try {
            long start = System.nanoTime();
            var bridge = new P03BlockingBridge(legacy, pool);
            StepVerifier.create(reactor.core.publisher.Flux.range(1, 10).flatMap(i -> bridge.customer("c" + i)).count())
                    .expectNext(10L).verifyComplete();
            assertThat((System.nanoTime() - start) / 1_000_000).isLessThan(400);         // 10 x 50 ms in parallel, not 500 ms
        } finally { pool.dispose(); }
    }
}

    Walkthrough¶

    Code Why
    Mono.fromCallable(() -> legacy.loadCustomer(id)) Lazy: the callable runs when someone subscribes, once per subscription, as the second test proves.
    .subscribeOn(blockingPool) Moves the subscription (and so the callable) onto the pool. Its position in the chain doesn't matter for the source.
    Schedulers.newBoundedElastic(10, 100, "legacy-crm") A bulkhead: at most 10 threads and 100 queued tasks for this dependency. The shared boundedElastic() is used by everything else.
    Mono.just(legacy.loadCustomer(id)) The classic trap: the argument is evaluated immediately, before any subscriber exists, on whatever thread built the pipeline. That's often the event loop.
    flatMap over 10 ids → < 400 ms Ten 50 ms calls run in parallel on the pool rather than one after another.

    Complexity¶

    Approach Time Space
    per call blocking time, on a pool thread 1 pool thread while running

    P03BlockingBridgeTest: 4 tests, 0 failures
  ✔ blocking call · runs on the dedicated pool · not the caller
  ✔ from callable · is lazy · nothing runs until subscribe
  ✔ many concurrent calls · do not serialise
  ✔ mono just · blocks the caller at assembly time

    Common mistakes¶

    • Mono.just(blocking()) or Mono.fromCallable(...) without subscribeOn: both block the event loop.
    • Using publishOn to fix a blocking source. publishOn only moves the operators after it.
    • Using Schedulers.parallel() for blocking I/O. It has one thread per core, and blocking them starves all CPU work.
    • Running a blocking JDBC repository inside WebFlux at high load. Prefer R2DBC, or use Spring MVC on virtual threads.

    Follow-up questions¶

    How do you detect accidental blocking calls?

    Use BlockHound (BlockHound.install() in tests): it throws when a blocking call such as Thread.sleep, socket reads or FileInputStream.read happens on a non-blocking thread. Reactor-tools' ReactorDebugAgent helps trace where it came from.

    With virtual threads, is WebFlux still worth it?

    For request/response services over blocking libraries, Spring MVC on virtual threads is simpler and often just as scalable. WebFlux still shines for streaming (SSE, WebSockets), backpressure, and composing many async sources.

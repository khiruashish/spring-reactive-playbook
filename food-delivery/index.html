    Food Delivery App — Capstone¶

    Everything from the previous tabs, composed into one reactive, event-driven microservice platform: browse restaurants, place an order, pay, and watch a courier move across the map live.

    Architecture¶

    flowchart LR UI[Browser UI<br/>EventSource + WebSocket] -->|HTTPS + JWT| GW[api-gateway :8080<br/>Spring Cloud Gateway] GW -->|/api/restaurants| RS[restaurant-service :8081<br/>functional endpoints] GW -->|/api/orders| OS[order-service :8082<br/>annotated controllers] GW -->|/api/deliveries| DS[delivery-service :8083] GW -->|/ws, /api/notifications| NS[notification-service :8084] OS -->|HTTP interface client| RS OS -->|WebClient + circuit breaker| PS[payment-service :8085] RS --- PG1[(PostgreSQL<br/>restaurant_db)] OS --- PG2[(PostgreSQL<br/>order_db)] DS --- MG[(MongoDB<br/>delivery_db)] OS -- OrderPlaced --> K{{Kafka}} K -- OrderPlaced --> DS K -- OrderPlaced --> NS DS -- DeliveryStatusChanged --> K K -- DeliveryStatusChanged --> OS K -- DeliveryStatusChanged --> NS

    Which playbook topics live where¶

    Service Reactive topics applied
    api-gateway Spring Cloud Gateway, global filters, ReactiveSecurityContextHolder, JWT resource server, WebSocket routing, static UI
    restaurant-service functional endpoints, R2DBC repositories with records, programmatic validation, onError → ProblemDetail
    order-service annotated controllers, ports & adapters, reactive transaction, idempotency, HTTP interface client, WebClient + retry + circuit breaker, Kafka producer/async listener, Sinks, SSE with heartbeat
    payment-service Mono.delay, failure injection, Mono.cache() for idempotent replays, virtual-time tests
    delivery-service reactive MongoDB, Flux.interval simulation, concatMap, Disposable lifecycle, SSE tracking
    notification-service Kafka → replaying Sinks.Many → WebSocket and SSE fan-out

    Event contracts¶

    // food.order.order.placed.v1  — key: orderId
record OrderPlaced(String orderId, String customerId, String restaurantId, long totalPaise,
                   String deliveryAddress, List<Line> lines, Instant placedAt)

// food.delivery.delivery.status-changed.v1  — key: orderId
record DeliveryStatusChanged(String orderId, String deliveryId, String courierId,
                             DeliveryStatus status, double latitude, double longitude, Instant at)

    Keying both topics by orderId keeps every event of one order on one partition, in order.

    Design rules used throughout¶

    • Money is long paise — never double.
    • Timestamps are Instant / TIMESTAMPTZ UTC.
    • Database per service; services reference each other by id only.
    • Idempotency: Idempotency-Key on order creation and payments; unique index on delivery per order.
    • No block() outside tests; every pipeline is returned to the framework.
    • Pure domain (Pricing, OrderStatus) is plain Java, unit-tested in microseconds.
